# 가상 연습: 비품 요청 검토

실제 시험·과거 대회 문제와 관계없는 새 가상 사례다. 완성 앱을 만들기보다 요구 확인 → 검사 → 설명 → 인계를 짧게 연습한다.

## 업무 요청

비품 담당자가 요청 목록을 보고 검토 상태와 메모를 남긴다. 취소 요청은 기본 목록에서 숨기며 별도로 확인할 수 있어야 한다. 현재 화면의 목록을 CSV로 내보낸다. 보류에는 사유가 필요하고, 새로고침 후 저장 상태가 유지돼야 한다.

```csv
ID,item,status,quantity
R001,키보드,active,2
R002,마우스,active,1
R003,모니터,cancelled,1
```

## 연습 순서

1. `clarify-work`: 기본 목록·취소 목록·내보내기의 범위와 저장 방식을 정리한다. 실제 담당자 확인 없이 새로운 승인 정책이나 금액 한도를 만들지 않는다.
2. `verify-with-evidence`: 기본 화면이 R001·R002 두 개라면 CSV도 같은 두 ID인지 검사한다. 아래 ‘의도적으로 잘못 만든 내보내기’는 실패를 찾기 위한 입력이며 정상 결과가 아니다.
3. `explain-your-work`: ‘왜 취소 요청을 기본 목록에서 제외했나?’, ‘세 개 모두 내보내면 어떤 혼동이 생기나?’, ‘어떤 검사로 확인했나?’에 사용자가 먼저 답한다.
4. `handoff-work`: 현재 기능, 실패·통과 검사, 미구현 저장 방식과 다음 행동을 구분해 인계한다. 아직 앱을 만들지 않았다면 구현 완료라고 쓰지 않는다.

실제 화면에서 확인한 ID 목록을 저장한 가상 입력:

```json
["R001", "R002"]
```

의도적으로 잘못 만든 내보내기:

```csv
ID,item,status,quantity
R001,키보드,active,2
R002,마우스,active,1
R003,모니터,cancelled,1
```

기대: 화면 2개와 CSV 3개가 다르고 R003이 추가됐다는 불일치를 찾아야 한다. 이 문서의 가상 입력은 실제 웹 화면을 검사했다는 증거가 아니다.

